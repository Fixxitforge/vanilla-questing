## 1. The three removed redraws — answering the question directly

The claim holds. **The argument in the repo is weaker than the evidence already sitting
in the repo**, and one case genuinely is less prompt than before.

### 1a. There is better proof than the source listing, and it is already in SPEC.md

The comment in `CVars.lua` rests on reading
`Blizzard_UIPanels_Game/Wrath/QuestMapFrame.lua:253`. That establishes what the client
*would* do if the branch runs. It does not establish that it runs.

But SPEC.md already records the in-game observation that settles it:

> `/vq on` in combat leaves the world map **open**. The AddOn cannot be doing it —
> `cycleWorldMap` returns before touching anything when `InCombatLockdown()` is true.

The only thing that opens the map there is
`QuestMapFrame:GetParent():HandleUserActionToggleQuestLog()` — **two lines above
`QuestMapFrame_UpdateAll()` in the same `if arg1 == "questPOI"` branch**. So the branch
demonstrably executes, on this client, in response to this AddOn's `SetCVar`. That is
an observation, not a reading.

- [ ] Cite the in-combat symptom in the `refreshQuestUI` comment as the evidence, with
      the source listing as the explanation of *what* runs. The rule this project wrote
      two commits earlier — reasoning about a mechanism is not evidence of which code
      triggers it — applies to this argument too.

### 1b. The strongest argument for removal is one the comment does not make

The comment argues *Blizzard already does it, so we do not need to*. There is a better
argument, and it does not depend on Blizzard's handler at all.

`cycleWorldMap` exists because, in this project's own words, still in the file:

> The on-screen quest helper only picks this up when the map pane is closed and
> reopened — reported from play, **and not fixed by asking the tracker to redraw.**

`WatchFrame_Update()` was *already known not to refresh the thing it was there to
refresh*. The call that was removed had been proven ineffective before it was removed.
Nothing is lost because there was nothing there to lose — regardless of whether
Blizzard's handler fires, whether it is registered, or whether a patch changes it.

- [ ] Put this in the comment. It is immune to everything that could falsify the
      current argument.

### 1c. The other five variables: "nothing is lost" is true by construction

`WatchFrame_Update` rebuilds the tracker; `QuestMapFrame_UpdateAll` rebuilds the map's
quest list. None of `autoQuestWatch`, `instantQuestText`, `showBosses`, `Outline` or
`ShowQuestObjectHighlightEffect` is read by either frame. The removed calls could not
have affected those five even when they were there. No test needed.

### 1d. One case IS less prompt, and it is not in the changelog

In v1.0.0 `refreshQuestUI` cycled the map for any `cyclesMap` rule unconditionally.
It is now gated on `ns.byRequest`, and the `CVAR_UPDATE` re-assert path leaves that
flag down.

So: another AddOn or Blizzard's own control moves `questPOI`, this AddOn writes it
back, and **the map is no longer cycled**. The on-screen helper does not get the round
trip that the file says is the only thing that refreshes it.

This is the right call — a re-assert is not someone asking for a refresh — but it is a
deliberate behaviour change relative to the last release and it is undocumented.

- [ ] Add a changelog line under **Changed**.

### 1e. Residual, low: is Blizzard's handler live before the map is first opened?

If `Blizzard_UIPanels_Game` is load-on-demand, the `questPOI` branch does not exist
until the world map has been opened once in the session. The only path that reaches
`refreshQuestUI` before that is the login path, where `byRequest` is false and nobody
is looking — so the practical risk is near zero.

- [ ] Cheap to settle: `/console reloadui`, do not open the map, `/vq off
      hideMapQuestHelper`, and see whether the map pane toggles. Record either answer
      in SPEC.md.

### 1f. A free finding: `CVAR_UPDATE` dispatches synchronously

Out of combat the cycle runs *after* Blizzard's toggle and the map ends closed; in
combat the cycle is skipped and the toggle is the last thing to happen. That ordering
is only possible if `CVAR_UPDATE` is dispatched inside the `SetCVar` call rather than
queued for the next frame.

That matters beyond this: the `applying` re-entry guard in `CVars.lua` assumes exactly
this and, in an earlier audit, I flagged it as an assumption that might not hold. It
holds, and now there is evidence for it.

- [ ] Record it in SPEC.md next to the guard.

## 2. Ship-blocker candidate: the map on a fresh install

**The changelog says:** "The world map no longer opens and closes by itself on a
loading screen."

**SPEC.md says** (#46): writing `questPOI` makes Blizzard's own handler call
`HandleUserActionToggleQuestLog()`, which toggles the quest log pane.

Follow the first login after a clean install. `hideMapQuestHelper` defaults on;
`questPOI` is at Blizzard's default of `1`; so the write happens. Blizzard toggles the
map **open**. `byRequest` is false, so the cycle that used to close it is skipped.

If that plays out as the code reads, the first thing a new user sees is the world map
opening by itself and **staying open** — where v1.0.0 showed it opening and closing.
That is worse than the behaviour the changelog claims to have fixed, in the one moment
that forms a new user's first impression.

The normal case is unaffected: `questPOI` persists between sessions, so on an ordinary
login nothing is written and nothing toggles.

The same mechanism fires mid-play on the re-assert path. Anything that sets `questPOI`
back to `1` — Questie's "Blizzard style objectives" option does exactly this — gets
written back by this AddOn, and the map pops open with no cycle to close it.

- [ ] **Test before tagging.** Delete `VanillaQuestingDB`, `/console questPOI 1`,
      reload, and watch the map.
- [ ] If it opens and stays open, either allow the cycle when a write actually
      happened (rather than when a person asked), or close the map once on the
      `CVAR_UPDATE` that follows our own write.
- [ ] Correct or remove the changelog line depending on the result.

## 3. The changelog

### The rule, and why it is not "everything, big and small"

Two rules, and the second is the one that answers this.

**Entries are relative to the last release, not the last commit.** A bug introduced and
fixed inside the same unreleased cycle has a net delta of zero and does not appear. A
reader of the changelog is a user of 1.0.0 deciding whether to update; churn between
`v1.0.0` and `HEAD` that they could never have experienced is noise. This is standard
across Keep a Changelog, the Linux kernel, Rust and Python.

**The test is reachability, not noticeability.** "Would anyone have noticed" is
unfalsifiable and, worse, it is an argument that always favours omission — it would
excuse hiding a real regression on the grounds that few people hit it. "Could a user of
1.0.0 have reached this code path" is checkable from git, and it makes the decision for
you.

Applied here, the original instinct on the tracking tooltip was **right, for a
different reason than the one given.** Not because nobody would have noticed — but
because the state was *unreachable* in 1.0.0. The commit that fixed it says so
outright: *"Eleven versions unnoticed because the state was unreachable. Until this
option became SHARED, ticking Track Quest POIs was overruled within the frame, so
nobody ever hovered that button with the option off."* Making the option stand down was
a 1.1.0 change. The bug was created and fixed inside this cycle.

A shipped-but-obscure bug is the opposite case and **does** belong in, briefly.
Somebody hit it, and they need to see it.

### Entries to change

- [ ] **Remove** — *"The minimap tracking button's tooltip no longer disappears when
      the option is off."* Unreachable in 1.0.0; the state was created by a 1.1.0
      change. Zero delta for a 1.0.0 user.

- [ ] **Remove** — *"Turning off the bag item highlight puts the highlights back at
      once, with your bags open."* I checked `git show v1.0.0:VanillaQuesting/Bags.lua`:
      `Disable()` called `ContainerFrame_Update` on every open container, which restored
      them at once. The behaviour is **identical** in both releases; only the mechanism
      changed, to drop a taint vector. The entry implies 1.0.0 was broken, which it was
      not. This is the same shape as the tooltip: a regression introduced and fixed
      inside the cycle.

- [ ] **Move out of Fixed** — *"The quest item buttons beside tracked quests are made
      invisible rather than hidden..."* Probe v0.32 found `WatchFrameItem1:IsProtected()`
      false, so no user ever hit a blocked action. Calling it a fix claims a bug that
      did not exist. It belongs under **Changed** as hardening, or in SPEC.md only.

- [ ] **Sharpen** — *"The AddOn no longer taints the game's quest tracker at login."*
      The second taint log showed login already clean and the remaining taint coming
      from the first `/vq on`. As written it under-claims the fix and misdescribes
      where the problem was. Suggest: "...at login or when you change an option."

- [ ] **Verify or correct** — the world map loading-screen line. See section 2.

### Entries to add

- [ ] **Changed:** the map no longer refreshes when a `questPOI` change is written back
      after something else moved it — only when you change the option yourself.
      (Section 1d.)
- [ ] **Changed:** Outline Mode's old saved setting is not carried across the rename.
      The migration drops it deliberately and `initDB` explains why well — but it is a
      user-visible consequence of updating, and only the changelog will tell them.

### One judgement call, your side to make

Two new options ship **on by default**, so updating from 1.0.0 changes the game for
existing users without asking: No Outline Mode and Remove Loot Sparkles. Each entry
does say "on by default", which is honest. A one-line note at the top of the 1.1.0
section aimed at upgraders would be kinder, and is common practice. Not a defect either
way.

## 5. Process

- [ ] **CI only runs on a version tag.** `release.yml` is the only workflow, triggered
      on `push: tags: v*`. Forty-eight commits landed on `main` with no automated check.
      The near-miss this cycle is the proof: deleting a comment block took four locals
      with it, `luac -p` accepted it because a call to a missing local is a legal nil
      global, and **luacheck caught it four days after being added for exactly that
      class**. A push-triggered workflow would have caught it on the commit.
      Add one that runs `dev/tests/run.sh` on push and pull request.
- Credit where due: the release job installs `lua-check` explicitly, with a comment
  saying why a developer's machine may skip it and a release runner must not. That
  reasoning is right. It is just undermined by the job only ever running at tag time.

## 7. What is in good shape

Stated because a list of defects is not a picture of the release.

- The taint work is the strongest thing in this cycle. Three logs, a hypothesis
  falsified twice, and a written rule out of it — *reasoning about a mechanism is not
  evidence of which code triggers it* — that is better than the fix.
- Both fixes were verified by reverting them and watching named checks go red. That is
  the part most people skip.
- The `outlineMode` → `noOutlineMode` migration refuses to invent a preference from a
  mirrored value. That is a subtle call and the comment argues it properly.
- Every finding from two previous audits is fixed, and the SPEC corrections are honest
  about what was wrong rather than quietly rewritten.
- 1047 checks across 17 failure scenarios, and the new ones assert that the removed
  redraws do *not* happen — so restoring them fails by name rather than by silence.
